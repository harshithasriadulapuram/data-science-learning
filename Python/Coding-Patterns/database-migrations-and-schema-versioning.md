
# Database Migrations and Schema Versioning

## 1. What Is a Database Migration?

A **database migration** is a controlled change to a database schema or, when appropriate, its data.

Examples include:
- Creating a new table.
- Adding a column.
- Adding an index.
- Changing a constraint.
- Renaming a column.
- Backfilling data into a new column.

As applications evolve, the database must evolve with them.

## 2. Why Are Migrations Important?

Imagine an application initially stores:

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100)
);
```

Later, the application needs an email address.

A migration can add the new column:

```sql
ALTER TABLE users
ADD COLUMN email VARCHAR(255);
```

A migration provides a recorded, repeatable way to apply that change across development, testing, and production environments.

Actual `ALTER TABLE` capabilities and locking behavior depend on the database engine.

## 3. What Is Schema Versioning?

Schema versioning records which database changes have been applied.

A migration system commonly maintains a table containing migration identifiers and application metadata.

For example:

| Version | Description |
|---|---|
| 001 | Create users table |
| 002 | Add email column |
| 003 | Add email index |

The migration tool tracks applied migrations so that previously executed migrations are not unintentionally reapplied.

## 4. Types of Database Migrations

### Schema Migration

Changes the database structure.

Examples:
- Create or drop a table.
- Add a column.
- Create an index.
- Add a foreign key.

### Data Migration

Transforms existing data.

Example:

```sql
UPDATE users
SET status = 'active'
WHERE status IS NULL;
```

This statement is appropriate only if assigning `active` is valid for every affected user.

### Forward Migration

Moves the schema or data toward a new version.

### Rollback Migration

Attempts to reverse a previously applied change.

Not every migration is perfectly reversible. For example, dropping a column destroys its stored values unless they have been preserved elsewhere.

## 5. Using Alembic with SQLAlchemy

Alembic is a database migration tool commonly used with SQLAlchemy.

Install the packages:

```bash
pip install sqlalchemy alembic
```

Initialize Alembic in a project:

```bash
alembic init migrations
```

This creates migration configuration and a directory for migration scripts.

Configure the database URL and, when using autogeneration, the SQLAlchemy model metadata in `alembic.ini` and `migrations/env.py`.

**Security note:** Do not commit production credentials in configuration files. Use environment variables or a secret manager.

## 6. Generate a Migration

After updating your SQLAlchemy models, generate a candidate migration:

```bash
alembic revision --autogenerate -m "add email to users"
```

Autogeneration compares model metadata with the database schema.

It is not perfect. Always inspect the generated migration and edit it when needed.

Autogeneration may not detect every change, including some data transformations, renames, or application-specific requirements.

## 7. Example Migration Script

A simplified Alembic migration might look like this:

```python
from alembic import op
import sqlalchemy as sa

revision = "002"
down_revision = "001"
branch_labels = None
depends_on = None


def upgrade():
    op.add_column(
        "users",
        sa.Column("email", sa.String(length=255), nullable=True),
    )


def downgrade():
    op.drop_column("users", "email")
```

The `upgrade()` function applies the change.

The `downgrade()` function attempts to reverse it.

Dropping the column during downgrade would delete its values. Before running a rollback, consider whether the data must be preserved.

The revision identifiers above are illustrative; real migrations should use unique identifiers generated by Alembic.

## 8. Apply and Inspect Migrations

Apply pending migrations:

```bash
alembic upgrade head
```

Inspect the current migration revision:

```bash
alembic current
```

View migration history:

```bash
alembic history
```

Move back one revision when a safe downgrade exists:

```bash
alembic downgrade -1
```

Run these commands against the intended database environment. A command executed against production can change production data or schema.

## 9. The Expand-and-Contract Pattern

Changing a database column can break older application versions that are still running during deployment.

The **expand-and-contract pattern** reduces this risk.

Suppose an application must rename `full_name` to `display_name`.

### Phase 1: Expand

Add `display_name` while keeping `full_name`.

### Phase 2: Migrate Data

Backfill `display_name` from `full_name` in manageable batches when necessary.

### Phase 3: Update the Application

Deploy application code that can work safely with the expanded schema. During a rolling deployment, older and newer application versions may coexist.

### Phase 4: Verify

Check that the new column is populated correctly and the application no longer depends on the old column.

### Phase 5: Contract

Only after dependencies have been removed, drop `full_name` in a separate migration.

This approach reduces compatibility problems during rolling deployments.

## 10. Zero-Downtime Migration Considerations

A migration can cause downtime if it blocks reads or writes, requires a long table rewrite, or conflicts with application versions.

Before a production migration:

- Review the database engine's locking behavior.
- Estimate table size and migration duration.
- Test with production-like data.
- Consider online index creation when supported.
- Backfill large datasets in batches.
- Monitor locks, replication lag, and application errors.
- Prepare a recovery plan.
- Coordinate application and schema changes.

A migration is not automatically zero-downtime simply because it runs automatically.

## 11. Database Migration Best Practices

1. Keep each migration focused and understandable.
2. Review generated migration scripts before applying them.
3. Test migrations on a disposable or staging database.
4. Back up important data before risky production changes.
5. Avoid destructive schema changes while older application versions still depend on them.
6. Use transactions where supported and appropriate.
7. Do not assume every database supports transactional DDL.
8. Make large data migrations resumable when possible.
9. Record and monitor migration failures.
10. Document any manual recovery steps.

## 12. Common Mistakes

- Editing an already-applied migration without a controlled recovery plan.
- Assuming a downgrade restores deleted data.
- Running migrations against the wrong database.
- Dropping a column before all application versions stop using it.
- Applying a large data transformation in one unbounded transaction.
- Trusting autogenerated migrations without reviewing them.
- Forgetting to test migrations against realistic data volumes.

## Key Takeaways

- Migrations make database changes trackable and repeatable.
- Schema versioning records which changes have been applied.
- Alembic integrates migrations with SQLAlchemy.
- Generated migrations must be reviewed and tested.
- Rollbacks may not recover destroyed data.
- Production migrations require careful planning for compatibility, locking, and recovery.
